# AM64x A53 Handover Implementation Plan (Full-Boot-Chain Phase 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The real chain continues past "Starting ATF on ARM64 core...": the
A53 cold-starts at the captured bootvector, BL31 + OP-TEE + A53 SPL +
u-boot proper run from the WIC, ending at the autoboot prompt on UART0.

**Architecture:** Three mechanisms. (1) The DMSC finally *acts* on proc-boot:
PROC_SET_CONFIG stores the bootvector per processor-id, and SET_DEVICE on the
A53 core devices (135/136) releases the matching vCPU via
`arm_set_cpu_on(affinity, entry, 0, target_el=3, target_aa64=true)` — no rvbar
games, lands in EL3h secure, and QEMU's PSCI is not registered in ROM-boot
mode so ATF's own PSCI rules. (2) Protocol hygiene: messages sent without the
AOP flag (WAIT_PROC_BOOT_STATUS 0xc401, the R5's shutdown SET_DEVICEs) must
get NO response — a pushed response would rot in the single-slot RX thread.
(3) OP-TEE enablers: bare-ACK the SA2UL/firewall TISCI messages and stub the
TRNG block — otherwise OP-TEE panics or hangs at its stack-canary refresh.
ATF/OPTEE/A53-u-boot sec-proxy channels are ALREADY wired (the existing
A53_0/1/2 DMSC clients match their thread pairs exactly).

**Tech Stack:** QEMU 10.2.50 fork, C, meson/ninja, qtest, tests/functional.

**Spec:** `docs/superpowers/specs/2026-07-15-am64-full-boot-chain-design.md` (Phase 3).
